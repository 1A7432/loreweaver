# 卡：把酒馆卡和原生卡带进房间

你手上有给酒馆（SillyTavern）做的人物卡和世界书，或者你在给 Loreweaver 写一个世界。这一页讲一张卡进入房间时会发生什么：什么能导入、什么真的会运行，以及因为这里是一个骰子是真骰子的游戏，卡的表现会在哪些地方不一样。背后的格式是 [LWF cards](lwf/formats/cards.md)（英文）；把卡放进扩展包见 [authoring.zh.md](authoring.zh.md) §4.1。

先记住一件事：Loreweaver 会**拆开每一张卡**（拆卡）。酒馆的“重卡”把一个角色和一整个世界——变量结构、模板、秘密设定——塞在一起，因为单人前端没别的地方放。在这里它们是两半：

- **人物那一半**——名字和人设——任何玩家都可以导入成自己的角色；
- **世界那一半**——设定、变量声明、模板、卡的常驻指令和开场——只有房间管理员能导入，因为它会改变整桌的玩法。

卡不会因为太重被拒：它会被拆开，每次导入都按数量说明留下了什么。

## 什么能导入

- **酒馆卡**，规范 v1、v2（`chara_card_v2`）和 v3（`chara_card_v3`），JSON 或带 `chara` / `ccv3` 文本块的 PNG，最大 16 MiB。读取的字段：`name`、`description`、`personality`、`scenario`、`first_mes`、`mes_example`、`creator_notes`、`system_prompt`、`post_history_instructions`、`alternate_greetings`、`tags` 和 `character_book`。不认识的字段直接忽略，所以新版酒馆导出的卡照样能导入。
- **世界书**放在卡的 `character_book` 里带进来。V2 的字段名和酒馆原生世界书的字段名都认。单独的世界书文件不是卡，什么也导入不了：把它的条目放进一张卡里。
- **原生卡**（`*.lorecard.json`，`"format": "loreweaver.card"`），Loreweaver 自己的格式。它装得下酒馆卡没地方安全存放的东西：只给守秘人看的（`secret`）条目、带类型的变量、逐条的条件、稳定的条目 id。样例见 [authoring.zh.md](authoring.zh.md#41-卡和设定)；字段见 [LWF cards](lwf/formats/cards.md) §2。

## 怎么导入

一张卡要么**作为世界**导入（房间管理员），要么**作为角色**导入（任何玩家）。

- **在客户端里。** 终端客户端和 Loreweaver Studio 会上传卡文件再执行导入。上传需要打开房间的上传开关（`.uploads on`，管理员操作）。只有上传文件的那个人能导入它。
- **从已启用的扩展包里**（扩展包清单里的 `kind` 写明这张卡是哪一半）：

  ```
  .import world <扩展包> <卡的路径>
  .import character <扩展包> <卡的路径> [名字]
  ```

  中文写法是 `.导入 世界 …` 和 `.导入 角色 …`。在聊天里安装扩展包时，回复会给出它带的每张世界卡的导入命令。
- **在命令行里**，以运营者身份：`loreweaver import-world <房间> <卡文件>` 把一张卡作为某个房间的世界导入。

协议层面（先上传，再 `command.run import`）见 [protocol.zh.md](protocol.zh.md) §11.6。

## 作为世界导入时带来什么

只有房间管理员能导入世界，守秘人不能通过工具来做。世界导入读取整张原卡：

- **设定。** 整本世界书成为房间的设定条目，按管理员的信任级别处理：`secret` 条目只给守秘人，`constant` 条目常驻。
- **变量。** `[InitVar]` 条目（标题里含 `[InitVar]`，方括号也算在内：`initvar notes` 是普通设定）给房间的变量树赋初值：容忍 JSON5 的对象或 YAML 映射，可以嵌套，路径可以是中文，叶子可以写成 `[值, "说明"]`。它们是数据，不是设定。原生卡带类型的 `variables` 成为房间的类型化变量。
- **留给守秘人。** 卡的正文（description、personality、scenario、对话示例、作者备注）、指令（`system_prompt`、`post_history_instructions`，去掉模板代码，`{{char}}` 绑定为卡名）和开场（`first_mes`、`alternate_greetings`）都留给守秘人。玩家只看得到这个世界的名字。
- **重新导入**同一张卡，会替换这张卡的设定，并保留房间里的变量值：房间已有的顶层键保留原值，所以重新导入不会把进度清零。导入*另一张*世界卡会叠加在第一张旁边（世界书扩展卡就是这么用的）；想从头来，就重置房间：先 `.reset all`，再 `.reset confirm`。

回复会数清楚进来了什么、没进来什么，比如「已导入世界 River Town：2 条设定（0 条保密），1 条变量声明，1 段开场。」3.0 不导入的：钩子脚本（3.0 没有钩子，只计数，绝不运行）和原生卡的 `pregens`。

没有任何东西会被截短塞进去。条件、标题、某个关键词或组名超过上限（条件 500 字，其余 200 字；关键词最多 64 个），或者开关字段的写法 Loreweaver 不认，这条设定就不导入，回复会说明有几条、为什么：「3 条设定未导入：开关字段不是 true 或 false ×2，条件过长 ×1。」卡里的其余部分照常导入。开关字段（`enabled`、`disable`、`constant`、`selective`、`useProbability`、`caseSensitive`、`matchWholeWords`、`groupOverride`）可以写成 `true`/`false`、`1`/`0` 或 `"true"`/`"false"`/`"1"`/`"0"`，和酒馆导出的文件一致；`secret` 只能是 `true` 或 `false`，条目本身或它的 `extensions` 里只要有一处写了 `true` 就是秘密。原生卡里的每个开关都只能是 `true` 或 `false`；写成别的样子的条目会被跳过，回复里会报告。

## 作为角色导入时带来什么

任何玩家都可以把一张卡导入成自己的角色。不管卡里有什么，它只写**一个角色和一个座位**：卡的名字，人设（description 和 personality）作为角色背景，以及按房间规则系统掷出来的一张角色卡。服务器配了模型时，角色卡会往模型从人设里读出的概念上靠，和 `genchar` 一样；模型不写任何数值，数值由规则系统来定。没有模型，或者超过了和 `genchar` 共用的每小时上限（每人 5 次），就直接掷，回复会说明原因。

世界那一半一样都不带——没有设定条目（普通条目也没有）、没有变量、没有模板、没有指令、没有开场——回复按数量列出来（英文界面原文）：

```
You now play River Town (CoC).
This is a world card: only its character came along; its world waits for the room admin's world import.
Left behind: variable declarations ×1, templates ×1, lore entries ×2, openings ×1.
```

## 什么会运行

世界导入之后，卡的机制会运行，记账由代码来做。

- **设定触发**，按酒馆世界书的规则：主关键词；次关键词的四种逻辑（AND ANY、AND ALL、NOT ANY、NOT ALL）；`probability`，由代码掷；区分大小写和全词匹配；`scan_depth`；`constant` 条目；`position`（`before` 和 `after` 决定唯一那一段设定里的先后，其它位置和别的条目一起排）；按回合计的定时效果（`sticky`、`cooldown`、`delay`）；包含组（每组按权重选一个）。服务器配了向量模型时，被语义召回找到的条目也算命中关键词。每个守秘人回合最多带 12 条、12,000 字的设定。正则关键词（`/…/`）按字面文字匹配。
- **装饰器。** `@@if <条件>` 设一个条件；`@@activate` 等同 `constant`；`@@dont_activate` 和只管渲染的条目（`[RENDER:` 标题、`@@render_*`、`@@iframe`、`@@message_formatting`）导入时设为停用，内容只剩状态栏残留的条目也一样。标题前缀 `[GENERATE:…]` 会被去掉。
- **模板（EJS）。** 设定条目可以是 EJS 模板。它们作为真正的 JavaScript 运行——EJS 库加 lodash——在房间的工作线程里，每次拼装提示词用一个全新的上下文，每个模板最多 1 秒，每次拼装最多 3 秒。接口沿用 ST-Prompt-Template：`getvar`、`setvar`、`incvar`、`decvar`、`getwi` / `getWorldInfo`（按标题取条目内容，停用的也能取）、`activewi`、`injectPrompt`、`getchar`、`getchat`、`define`、`execvar`、`SafeGetValue`、`print`、`variables`、`stat_data`，lodash 是 `_`。模板里的写入只是请求，之后由引擎代码执行（每次拼装最多 64 条）。出错的模板渲染成空，绝不会原样输出：原始模板语法永远到不了模型面前。开场白在说出来之前也像设定一样渲染。
- **条件**（`@@if`、原生卡的 `condition`）先用 Loreweaver 的条件语言读；读不了的，在工作线程里当 JavaScript 求值。出错就意味着这条不进。
- **宏。** `{{user}}`（当前的玩家角色）、`{{char}}`（卡名，导入时绑定）、`{{time}}` / `{{date}}`（游戏内时钟）、`{{roll:XdY}}`（由骰子引擎掷）、`{{random}}`、`{{pick}}`、`{{getvar::name}}`、`{{var:name}}`、`{{newline}}`、`{{trim}}`、`{{// 注释}}`。
- **MVU 协议。** 模型可以写 `<UpdateVariable>` 块，用 `_.set` / `_.insert` / `_.delete` / `_.add`；代码解析它们，写进变量树，再从玩家看到的文字里删掉。一条长到没法检查的回复（超过 500,000 字）如果可能含有这种块，就整条不显示；这一回合失败，可以重试。守秘人还有带结构校验的工具操作同一棵树。

## 变量，以及玩家能看到什么

导入的变量树是模组的状态，重卡常把剧情标记放在里面，所以它一开始**完全隐藏**：房间管理员公开之前，玩家一片叶子都看不到。

```
.var list                    列出所有变量，隐藏的会标出来
.var expose town             玩家从此能看到 town 和它下面的一切
.var hide town
```

一个前缀公开它自己和它的子树，按段对齐（`town` 公开 `town.flood`，不公开 `town2`）；`*` 公开全部。管理员自己看到的永远是整棵树，隐藏的叶子带标记。原生卡的类型化变量对玩家可见，除非写了 `"visibility": "keeper"`；任何别的写法（包括 `"Keeper"`）都会被拒绝并给出警告，绝不会变成玩家可见。面板通过 `variables` 视图读变量，所以面板永远不会显示隐藏的叶子。告诉你的玩家该公开哪些前缀，比如写在扩展包里这张卡的 `notes` 里。

## 让卡里的开关真的能拨

有些重卡带一个开局向导：一组导入时就停用、没有关键词的条目——难度档、路线分支——加一段前端脚本，把选中的那条打开。Loreweaver 照样导入这些条目，但不运行前端脚本，所以没人去打开它们。世界导入会按数量说明：「N 条设定处于停用状态且没有关键词」。房间管理员可以不动卡本身把它们打开：

- **看哪些是关的：** `.lore list disabled`。`.lore list` 会给条目标上 `[关]`、`[秘密]` 和 `[已批注]`（这个房间改过文件里的设置）。
- **手动开关：** `.lore enable <标题>`、`.lore disable <标题>`。
- **绑到一个变量上：** `.lore bind <标题> | <条件>`，比如 `.lore bind Hard mode | town.flood >= 4`。条件成立时这条进，不成立时不进；三条分别绑到同一个变量的三个值上，就和卡里的单选按钮一样。`.lore unbind <标题>` 清掉条件；`.lore restore <标题>` 把这条交还给文件。
- **改一个值：** `.var set <路径> <值>`、`.var add <路径> <增量>`。
- **控制模板也行：** 一条启用的条目可以拉进一条停用的，`<%- getwi("Difficulty: " + getvar("config.difficulty")) %>`。

这些开关存成一份只给守秘人的覆盖层，放在设定旁边，从不写进设定本身，所以重新导入修订过的卡也会保留它们。Loreweaver 从不猜你要哪个分支：它不从标题里读结构，也不把条目归成一组。3.0 里扩展包不能替卡带这些开关（2.x 有 `overlay:` 文件），由房间管理员来设。

## 这里有什么不一样

- **骰子是真的。** `{{roll}}` 和每次检定都由骰子引擎掷；卡没法凭空写出一个结果。
- **数值要校验。** 导入的角色会成为房间规则系统下的一张角色卡，受它的上限约束。
- **`{{time}}` 和 `{{date}}` 是游戏内时钟**，不是现实时间。
- **随机可以复现。** `{{random}}`、`{{pick}}`、设定的 `probability` 和模板里的 `Math.random` 都按房间和回合取种子：重试同一回合，抽到的值一样。模板里的 `Date` 在一次拼装中固定不变。
- **`faker` 返回空字符串**，按消息序号定位的 `@INJECT` 不起作用：Loreweaver 自己拼一份提示词。
- **状态栏和只管渲染的条目**导入时就停用。扩展包要在客户端里画界面，用面板（[authoring.zh.md](authoring.zh.md#44-面板)）。

## 导入信任边界

导入的文件不能自己决定自己的权限。

- **拆卡靠代码，不靠提示词。** 角色导入只写一个角色和一个座位；不管卡怎么写，它都加不了设定、种不了变量、带不进模板代码。
- **`secret` 和 `constant` 是管理员的。** 只有世界导入会保留秘密条目或常驻条目。`secret` 不是 `true` 或 `false` 的条目绝不会被当成公开的：它不给玩家看，也不会被导入。
- **条目固定在导入它的房间里**，id 会重新生成，所以一张卡碰不到另一张卡的条目。
- **秘密就是秘密。** 玩家的设定列表、面板和其它所有视图都由服务器逐人计算；秘密条目、只给守秘人的变量、没公开的叶子，永远不会出现在玩家的视图里。为玩家级读者渲染的模板也读不到秘密条目。
- **模板是管理员选择运行的代码。** 它们在房间的工作线程里运行，有时间上限，碰不到服务器的对象，但单个上下文没有自己的内存上限：世界导入就是管理员决定运行这张卡的模板，和酒馆一样（“你的机器，你的卡”）。没有关闭模板的开关。

## 3.0 里没有的

卡里的钩子脚本（`extensions.loreweaver_hooks`、原生卡的 `hooks`）只计数、报告，绝不运行：对回合作出反应的代码，是扩展包里的模组（见 [sdk/README.md](../sdk/README.md)，英文）。同样没有了：把卡导入成 AI 同伴、原生卡可认领的 `pregens`、单独的世界书文件、`.lore import`，以及扩展包的 `overlay:` 文件。
