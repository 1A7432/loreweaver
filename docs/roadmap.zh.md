# Loreweaver 路线图

Loreweaver 还很年轻，基本是一个人带着 AI 写出来的。这份是老实的前进计划：3.0 重写做完了什么、还没做什么，以及一个曾经真的犹豫过、现在已经定下来的设计问题。分层契约和铁律在 [AGENTS.md](../AGENTS.md)。

## 想做成什么

目标不是“拿 AI 顶替一个主持人”，而是做 **AI RPG 的引擎与开放标准**。会写代码的 agent 到处都是，能把一场团跑好的却几乎没有；而一个世界要想被带走、被续写、被别人的程序读懂，需要的格式压根还不存在。这里每一层——真骰子和硬规则、靠工具调用做事的守秘人、只知道自己该知道那部分的子角色、照着 SKILL.md 和酒馆惯例长出来的扩展生态——都朝同一个方向：让“把一个世界跑好”成为 agent 的一等能力，而且跑在谁都不用申请许可的格式上。

## 现在到哪了：3.0

3.0 用 Bun 和严格模式的 TypeScript 把 Loreweaver 重写成一个新项目：新的协议（3.0），和 2.x 在协议、房间数据库、内容包和模组格式上都不兼容。酒馆卡导入保留了下来。2.x 的 Python 服务器已经从这个分支删掉。重写之后已经有的：

- **一个工作区。** 服务器、模组 SDK、协议包和终端客户端是同一个 Bun 工作区。服务器能编成单个文件，它自带的自检会用脚本化的模型跑一个真实回合；CI 在 Linux（x64 和 arm64）、macOS、Windows 上构建这个文件并跑自检。
- **只有一份说明的协议。** [docs/protocol.md](protocol.md)，照着代码写：带编号的事件日志，日志有代次（撤销、重置、导入都会让房间换到新一代）；服务器替每个观看者维持最新的视图；引擎、规则系统和模组的命令共用一张命令表；文件走单独的字节通道。协议包里有类型、解码器和一个参考客户端会话；有一个测试把真客户端接到真服务器上，对比两边的日志。
- **一次只做一件事的房间。** 发言和命令在每个房间的一把锁后面按到达顺序排队；只有一句发言才会开一个守秘人回合。撤销、重置、导入不等锁：旧一代还在跑的东西，会自己以过期收场。
- **模组是真代码。** 内容包里的模组跑在房间自己的 worker 线程里，从不上服务器主线程；它们通过效果来回应，由引擎校验后执行。模组 SDK（[sdk/README.md](../sdk/README.md)，英文）里有接口约定和测试宿主。
- **内容包，manifest 3。** 一个 `.lwpack` 装着模组、规则系统、技能、卡、面板、演出资料包和素材；写入任何东西之前先整体校验，信任卡第一句就说它跑不跑代码。由跑服务器的人安装，或者由房间管理员在牌桌上装；按房间启用。
- **规则是数据，文档是唯一的出口。** CoC 7e、D&D 5e SRD、WoD 都是规则包；房间里的所有内容都是文档，`project(document, viewer)` 是内容发往连接的唯一途径，每种类型都有专门盯泄漏的测试。
- **有上限的回合。** 一个守秘人回合最多 21 次模型调用，有测试盯着；书记官、演出导演、NPC 发言、编年史折叠都是登记过的车道，每一处模型调用都要登记车道，否则构建失败。
- **牌桌上的东西。** 按规则系统掷骰建卡、按描述生成（`.genchar`）、从卡导入；自包含网页版的团报；三层音频；敏感词过滤；运行时切换模型；终端客户端里的访问钥匙和模型两屏。

## 3.0 还没有的

- **发布版本。** 3.0 还没有发布任何构建：没有安装脚本，没有可下载的包，没有自更新。现在要用 Bun 从源码运行。npm 上的 `loreweaver-protocol` 还是 2.6；3.0 的包在这个仓库里。
- **桌面客户端。** Loreweaver Studio 正在它自己的仓库里迁到 3.0，现在还连不上 3.0 的服务器。
- **运行页面。** HTML 页面形式的面板会被列出、也能取到，但还没有客户端会跑它；终端客户端画的是它的降级版。房间在运行时发布的面板只是预留，没有实现。协议里的 `features` 和 `caps` 是空的，有几个信号（`turn.activity`、`turn.round`、`notice.spinner`）定义了但不发送——见 [protocol.md §14](protocol.md#14-not-in-30-yet)。
- **从客户端备份。** `.save` 能把房间导出成一份存档，但终端客户端还不会把它写成文件；现在的备份办法是复制数据目录。
- **每晚自动跑的真模型实测。** 真模型实测（`server/eval/playtest.ts`）目前是手动跑。
- **2.x 有、3.0 没有带过来的：** 聊天平台桥接（包括 QQ 桥接）；WebSocket 通道；Docker；`hooks.js` 和 QuickJS 沙箱，规则包的脚本通道也随之没了（取而代之的是在房间 worker 里跑的真代码模组）；AI 同伴；按一句描述生成技能、规则系统或模组的生成器；Gemini 原生客户端和 ChatGPT / SuperGrok 订阅接入；酒馆的提示预设；地图；演示模式；`doctor` 和 `lint` 两个命令；实时重载的开发房间；工具调用记录文件。

## 近期

- **第一个 3.0 发布版本**，给各个平台编好单文件服务器，让一桌人不用源码也能玩。
- **桌面客户端迁到 3.0。** [loreweaver-studio](https://github.com/1A7432/loreweaver-studio) 是图形客户端，也是制卡和打包的工作台；在它说上 3.0 协议之前，先用终端客户端玩。
- **把多人联机打磨好。** 把联网游玩剩下的毛边磨掉，让一群互相信任的人在一个房间里玩得真正舒服。
- **一个旗舰模组。** 格式值多少，取决于在它上面做出的第一件正经东西；这件东西正在 3.0 上做，和面板、演出层一起设计，让这两层有一个真实的使用者，而不是假想的。

## 更远的方向：世界引擎

真正让它不一样的，是冒险*底下*的那个世界，而不是一个绑了骰子的聊天框。长远方向：

- **可深度定制的界面扩展层。** 模组和内容包应该能自己**画**界面——现在是声明式区块和模板面板，下一步是能在富客户端里跑的页面——这样一个世界带出去的不只是规则和设定，还有它自己的牌桌布置。协议客户端就是渲染目标。
- **更深的世界书：** 会生成的世界（不只是按关键词、向量检索出来的设定），一条**活的因果时间线**，事件会产生后果并一路传下去，再加上**正史一致性**，让守秘人没法和已经确立的事实打架。
- **给中途加入的人补课：** 半路进来的人，会被告知他的角色*本来就该*知道的事——而他的角色不该知道的，一个字都不给。
- **导入 D&D Beyond 角色卡**，和现有的酒馆卡导入并列。

## 一个已经定下来的问题，以及怎么定的

**守秘人的秘密放在哪？** 这一度是个真正的岔路口。守秘人的提示里装着世界的守秘人专属材料，守秘人专用的工具也会把秘密原文交回去——所以在守秘人自己这一侧，挡住剧透的是一条“别引用这些材料”的指令，而不是代码的结构。另一条路是让基础提示里不放秘密，让守秘人按需去取，这样模型手里永远只有它刚推理过的那一条。

**我们决定不这么做。** 不知道全部真相的守秘人主持不了谜案：它埋不下伏笔、揭示的时机会错，两场之后还会自相矛盾。限量供应守秘人自己的知识，等于拿这个产品存在的意义去换一点更小的泄密风险——而这点风险，用真模型测试就能直接对付。所以这个划分是永久的、故意的：

- **对其他所有人，靠的是代码。** 玩家、NPC 和演出导演拿到的都是过滤过的视图，别的什么都没有。有专门的测试，一旦这一点不再成立就会报错。
- **只对守秘人，靠的是行为。** 它看得到模组。它被要求不要引用。这条要求会拿真模型去*测*，但从不当成保证来宣称。

老实的说法写在 README 和 [deploy.zh.md](deploy.zh.md#数据流向与信任边界) 里，也会一直写在那里：CI 绿了，说明引擎是对的，不说明守秘人嘴严。

## 离线测试和真模型质量

值得说清楚，因为一个绿色的 CI 徽章很容易被读得太乐观。离线测试是确定性的，用的是*脚本化*的模型。它能把机械那一半证明扎实——守秘人材料不会混进玩家材料、每个 NPC 只用它自己的档案拼出来、骰子是真的而且有固定种子、命令说做什么就做什么——这些哪一条坏了它都能抓到。它**证明不了**的是：一个活的模型看过秘密之后会不会守口如瓶，会不会先掷骰再叙事。这些是模型的行为，正是真模型实测要去量的东西。“CI 是绿的”请读成*引擎是对的*，而不是*守秘人是好的*。

## 怎么帮忙

上面任何一条都可以挑。提 PR 之前，`server/`、`sdk/`、`clients/tui/` 里的 `bun run check`，`clients/protocol/` 里的 `bun test`，以及 `server/` 里的 `bun run build` 都要通过，并且守住 [AGENTS.md](../AGENTS.md) 里的铁律：不写死任何给人看的文字，该由代码决定的事绝不交给模型，信息隔离一次都不能破。
